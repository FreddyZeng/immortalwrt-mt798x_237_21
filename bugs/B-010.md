# B-010: 宽基线审计发现的 QoS 链顺序与遗留脚本污染

<!-- BID: B-010 | FID: F-QOS01 | 修复 CID: C-FQOS01-07 | 日期: 2026-05-03 -->

## 等级
P1

## 现象
- `init.d/eqos` 在 `/usr/sbin/eqos start` 之后再次 flush 并挂载 IPv6 `eqos` 链，最终可能形成 `eqos_apply` 先于 `eqos` 的 FORWARD 顺序，IPv6 NEW 首包无法在同一包内 restore 低 8 位 QoS mark。
- Software tc 模式仍会安装旧 `MARK --set-xmark 0x99/0xFF` 规则，`0x99` 含 bit7，HNAT 会把该低位 mark 误判为下行硬件限速并送入 Q63。
- `eqos_origin` 作为旧脚本位于 `root/usr/sbin`，会被包安装进固件，保留旧 MARK/DSCP 架构和 `/bin/sh` 不兼容语法。

## 根因
- IPv6 链生命周期被 init.d 和 `/usr/sbin/eqos` 两个入口共同管理，破坏了 `eqos -> eqos_apply` 的首包标记顺序。
- 软件限速分支保留了旧硬件 mark 兼容逻辑，但当前 HNAT 已把低 8 位 mark 作为语义位域解释。
- 旧版备份脚本放在 LuCI 包的 `root/` 安装树下，不是仓库私有参考文件。

## 修复
- IPv6 `eqos`/`eqos_apply` 链只由 `/usr/sbin/eqos` 创建、清空、去重和挂载；init.d 不再触碰 IPv6 mangle 链。
- `/usr/sbin/eqos` 在 IPv6 启用时循环删除重复 FORWARD jump 后按 `eqos` 先、`eqos_apply` 后的顺序追加，并记录 `[EQOS-C-FQOS01-08-01]` 诊断日志。
- Software tc 分支只循环清理旧 `MARK 0x99` 规则，不再追加任何旧 MARK 规则，避免污染 HNAT 低位语义 mark。
- 删除 `root/usr/sbin/eqos_origin`，避免旧架构脚本被安装进固件。

## 验证
- `sh -n package/mtk/applications/luci-app-eqos-mtk/root/usr/sbin/eqos`
- `sh -n package/mtk/applications/luci-app-eqos-mtk/root/etc/init.d/eqos`
- `sh test/qos-regression.sh`
