# Bug Report: B-005

## Title
CAKE vs HNAT Priority Asymmetry for 109 Subnet

## Description
在进行全量深度审计时发现一个优先级的“微小不对称”：
- **硬件 HNAT 侧**：针对 `192.168.109.x` 的游戏 UDP 小包（<=300B），下载方向被强制分配了 `dscp = 48`，对应的硬件队列为 `Q33` (CS6，属于第二高优先级，把 `Q32` 最高优先级留给了真实的 VIP IP/MAC)。
- **软件 CAKE 侧**：在 `sch_cake.c` 中，`is_nat_target_ip_109_k(skb)` 一旦命中，直接返回了 `&q->tins[highest_priority_tin]`，也就是将 109 的包放进了软件层的最高优先级 `Tin 7`。

这导致软件（CAKE）和硬件（HNAT）在对待 109 游戏网段时，优先级出现了 1 级的错位。为了保证软硬一体的完美对称，并且防止 109 网段的流量抢占真 VIP 流量的 CAKE 令牌，必须在软件层同样将其降级为 `Tin 6` (即 highest_priority_tin - 1)。

## Root Cause
在编写 `9999992-add-109-vip-small-udp.patch` 时，为了快速让 109 小包跑进高优队列，直接复用了 `return &q->tins[highest_priority_tin];`。未与后续硬件层的 `dscp = 48` -> `Q33` 进行对齐。

## Resolution
修改 `target/linux/mediatek/patches-5.4/9999992-add-109-vip-small-udp.patch`：
```c
+			if (q->tin_cnt > 1 && highest_priority_tin > 0)
+				return &q->tins[highest_priority_tin - 1];
+			else
+				return &q->tins[highest_priority_tin];
```
这样在多 Tin 模式下（比如 diffserv8），109 小包将安全降落至 `Tin 6`，与硬件的 `Q33` 形成完美的语义对应。
