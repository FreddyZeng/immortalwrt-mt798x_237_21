# B-001: QoS 回归审计修复

<!-- BID: B-001 | FID: F-QOS01 | 修复 CID: C-FQOS01-02 | 日期: 2026-05-02 -->

## 等级
P1

## 现象
- IPv6 硬件限速设备上行只写旧 MARK/DSCP 单值，无法表达上传、下载两个独立限速方向。
- 旧版 `comment` 文本配置进入数值比较，导致 `eqos add` 在设备规则生成阶段报错。
- 硬件限速速度为 0 时仍安装单值限速分类，且 HNAT/CPU TX 对可信 mark 的识别曾混用 raw qid，可能误接收其他 fwmark。
- CAKE 补丁栈最终态的 `highest_priority_tin` 在单 tin 模式下缺少确定初值，且 `TC_PRIO_MAX` 可绕过 VIP 范围判断。
- 验证脚本把 DSCP 41-45 展示为固定优先队列，与 HNAT `dscp_to_queue()` 实际映射不一致。

## 根因
- `eqos add` 未在数值比较前归一化 QoS mode。
- IPv6 限速分支缺少与 IPv4 对称的方向语义，旧单值分类不能区分上行 Q31 和下行 Q63。
- 限速分类规则未按方向检查速度是否为 0；HNAT/CPU TX 曾使用 `skb->mark & MTK_QDMA_TX_MASK` 识别策略 mark，使非 QoS mark 存在低位碰撞风险。
- CAKE 补丁栈在插入 VIP 和 109 小 UDP 最高 tin 保护时未覆盖 tin_cnt 边界，并保留了直接最高 tin 分支。
- 验证脚本维护了独立队列说明，没有复用 HNAT 的真实映射语义。

## 修复
- 非数字 QoS mode 归一化为硬件限速模式 0，并记录 debug 诊断日志。
- 限速设备统一使用 ct_mark 方向位：上行写入 `0x40/0xC0`，下行写入 `0x80/0xC0`，双向写入 `0xC0/0xC0`；`eqos_apply` 只在匹配方向同步 DSCP2，HNAT 识别 `(qos_mark & 0x40) && UPLOAD → Q31`、`(qos_mark & 0x80) && DOWNLOAD → Q63`。
- 限速速度为 0 的方向不再安装对应方向 bit；HNAT 和 CPU TX 只识别可信语义 mark（46、0x40、0x80、0xC0），其他低位 mark 回退到 DSCP/hash 或普通队列。
- 新增 `9999995-fix-cake-highest-tin-guard.patch`，在补丁栈最终态上将 `highest_priority_tin` 初始化为 0，VIP 和 109 小 UDP 检查限制在 `tin_cnt > 1`，priority、mark、DSCP 三条降级路径都保护单 tin 边界，并移除 `TC_PRIO_MAX` 最高 tin 绕过。
- 验证脚本改为按 HNAT 映射展示 Q0-Q31/Q32-Q63，删除 DSCP 41-45 固定 SP 标签。
