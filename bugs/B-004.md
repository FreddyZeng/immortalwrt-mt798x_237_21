# B-004: Legacy `--set-mark` Usage Corrupts Upper Routing Bits (mwan3 Conflict)

## 1. 症状描述
在执行 `CONNMARK` 0xFF 掩码架构重构后，`eqos` 脚本中仍残留使用老式 `--set-mark 0x99` 和 `--set-mark 2"$interface"` 的 iptables 命令。这会导致 iptables 直接全零覆盖上层 24 位的标志位，直接破坏 `mwan3` 的路由标记（`0x3F00` 范围）。

## 2. 根因分析
- **历史遗留**: 在引入 0xFF 掩码隔离机制之前，由于未考虑 multi-wan，旧代码直接使用 `--set-mark` (隐含掩码 0xFFFFFFFF) 设置 QoS tag。
- **冲突点**: `mwan3` 在 `PREROUTING` 链打上的路由选路标记存储在高位，而 `--set-mark` 强行清空了高位。

## 3. 修复方案
- 将所有的 `--set-mark 0x99` 替换为 `--set-xmark 0x99/0xFF`，保证只在低 8 位上操作，不破坏上层路由 bit。
- 将 PREROUTING 阶段设置 mwan3 出口标记的 `--set-mark 2"$interface"` 替换为 `--set-xmark 2"$interface"/0xFF00`，只在第二字节（`0xFF00`）执行 XOR，防止破坏低 8 位的 QoS Mark。

## 4. 影响范围
- QoS 分流逻辑
- 多线负载均衡 (mwan3) 稳定性

## 5. 验证状态
已全量扫描 `eqos` 脚本并修正，无遗留 `--set-mark` 语法。

## 6. 内核侧连带修复 (Kernel-side counter-fix)
在修复用户态脚本为 `--set-xmark 0x99/0xFF` 后，因为此时高位可能带有 mwan3 的 `0x100` 等标记，导致 `skb->mark` 在内核里不再等于单纯的 `0x99` (而可能是 `0x199` 等)。
因此，同步修改了 `target/linux/mediatek/files-5.4/drivers/net/ethernet/mediatek/mtk_hnat/hnat_nf_hook.c`：
将所有的 `if (unlikely(skb->mark == HNAT_EXCEPTION_TAG))` 
强制变更为 `if (unlikely((skb->mark & 0xFF) == HNAT_EXCEPTION_TAG))`。
保证 HNAT 在判断是否将数据包踢回 CPU 慢速路径时，同样严守 `0xFF` 掩码规范！
